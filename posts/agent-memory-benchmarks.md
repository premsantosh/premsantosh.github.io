I wrote about the big "Memory in the Age of AI Agents" survey (arXiv 2512.13564) a while back. The taxonomy stuff (forms / functions / dynamics) is fine but honestly the part I keep coming back to is Section 6, the benchmarks compilation. For anyone building an agent memory system, this is the practical question: how do you actually know your thing works?

I've been wrestling with this for Friday. It's easy to build a memory pipeline that looks impressive on demos and falls apart the moment you ask "but is it actually retrieving the right thing?". Benchmarks are how you stop fooling yourself.

So this post is my notes on the main benchmarks the survey lists, what they actually measure, and which ones I think are worth caring about if you're building real systems vs. writing papers.

---

#### Why Benchmarks for Memory Are Weird

Quick aside before I get into the list. Memory benchmarks are a strange beast compared to most ML evals.

For something like image classification you have a held-out set, you run inference, you compute accuracy. Done. Memory is harder because:

1. **The eval is path-dependent.** What the system remembers at turn 100 depends on what happened at turns 1 through 99. You can't just shuffle test examples and rerun.
2. **Write-time and read-time are coupled.** A bad ingestion choice at turn 5 will silently hurt retrieval at turn 50, but the failure mode looks like a retrieval bug.
3. **"Correct" is fuzzy.** If the user said "I prefer oat milk" in session 3 and "I switched to almond" in session 7, what's the right answer in session 10? Depends entirely on whether you're testing "knowledge updates" or "factual recall".

This is closer to evaluating a stateful streaming pipeline than a stateless model. You're not measuring a function, you're measuring a system over time. The benchmarks below handle this with various degrees of care.

---

#### LongMemEval (Wu et al., 2024)

This is basically the de facto standard for conversational memory right now. Pretty much every memory paper from 2024 onwards reports LongMemEval numbers, including Mem0, Zep, Hindsight, MemMachine, A-Mem — everyone.

500 manually-written questions across five capabilities:

- **Information extraction** — can you pull a fact someone mentioned earlier
- **Multi-session reasoning** — combining facts across sessions
- **Temporal reasoning** — "what was true as of last Tuesday"
- **Knowledge updates** — handling "I changed my mind" / "I moved to a new city"
- **Abstention** — knowing when you *don't* know something

The clever bit is the haystack construction. They take a real Q+context pair and pad it with unrelated dialogue sessions to whatever length you want. So you can run the same questions at different effective context lengths and see where your system breaks down. Like a long-context stress test but for memory.

What I like: the abstention category. Most benchmarks reward you for guessing. Abstention specifically tests "do you know that you don't know", which in production matters way more than people admit.

What I don't like: the questions are *manually written*, which means 500 of them. Statistically thin. You can game it with prompt engineering, and I suspect a lot of the recent 90%+ numbers (Hindsight, MemMachine) are doing exactly that.

---

#### LoCoMo (Maharana et al., 2024)

The other one everyone runs. 50 long-term chat histories, with questions covering single-hop, multi-hop, temporal, commonsense, and adversarial reasoning. Older than LongMemEval (came first) and somewhat narrower in what it tests.

If I'm being honest LoCoMo is mostly there because everyone already reports it. The benchmark itself isn't that great — questions can feel artificial, and the conversations were generated by an LLM persona-playing humans, which is a bit circular. But it's the only paired comparison number you can get against the existing papers, so it stays in the suite by inertia.

Same vibe as YCSB in database land — everyone knows it's not perfect but you publish numbers on it because that's what comparison requires.

---

#### StreamBench (Wu et al., 2024)

This one's underrated. Tests *lifelong learning* in agents — can the agent get better at a task over time as it accumulates experience.

The setup: agent solves a stream of tasks one after another, has access to its own past attempts, and you measure whether accuracy improves over the stream. So you're not measuring "can it recall facts" but "can it learn from experience".

This maps directly to what I actually want from Friday. I don't really care if it can recall every fact from every conversation. I care if it gets better at *me* over time — learning my patterns, my preferences, my projects. StreamBench is the closest published thing to that.

The catch: the tasks in StreamBench are pretty narrow (mostly QA-style), so it's not a perfect proxy for "personal assistant gets smarter". But conceptually it's the right shape.

---

#### GAIA / XBench / BrowseComp

These are the "deep research" benchmarks — complex multi-step problems where the agent has to plan, use tools, browse the web, and synthesize. They're not memory benchmarks per se, but the survey includes them because long-horizon agentic work *requires* working memory to track what you've already tried, what worked, what dead-ended.

If you're building an agent that does multi-step research tasks, the memory component shows up implicitly: better working memory = fewer redundant searches, fewer "wait I already looked at that" moments. So these end up in the memory eval mix.

For Friday these are mostly irrelevant — it's a personal assistant, not a research agent. But useful to know they exist if you ever swing in that direction.

---

#### SWE-bench Verified

Code agents fixing real GitHub issues. The verified subset (curated by OpenAI) is the high-signal version — cases where the patches actually verify against test suites.

Why it shows up in a memory survey: the agent has to remember what files it's touched, what it's tried, what errors it hit. A coding agent without working memory just thrashes. The "memory" in this case isn't long-term across sessions, it's structured working memory within a single task.

If I had to pick one benchmark for "your agent's working memory is competent", SWE-bench Verified is probably it. It's hard, it's real, it doesn't have an easy gameable surface.

---

#### MEMENTO

Multimodal embodied memory. Robot/embodied agent has to remember spatial and perceptual context across an interaction. Not directly relevant to most LLM agent work, but interesting as a pointer to where this is going — multimodal memory is going to matter once these things have eyes.

#### What Bothers Me About the Current Benchmark Landscape

**Most benchmarks ignore the cost dimension.** They report accuracy. They don't report how many tokens you spent at ingestion time, how much storage you accumulated, how slow retrieval got. For production this is everything. A memory system that gets 95% on LongMemEval but costs $0.50 per turn is worse than one that gets 85% at $0.005. Nobody publishes that table.

**Eval is single-shot, real usage is streaming.** Benchmarks run a fixed conversation, ask questions at the end, score. In real life you're answering questions *while* the conversation continues, your memory is changing under you, and you have to handle race conditions between writes and reads. None of the benchmarks test this.

**The "memory" being tested is usually just retrieval.** Almost every benchmark reduces to "did you pull the right span back into context". That's RAG with a few extra steps. The harder questions — did the system *consolidate* memories correctly, did it *forget* the right things, did it resolve contradictions — barely show up. Knowledge updates in LongMemEval is the closest thing and even that's limited.

**No benchmark tests temporal drift.** What does your memory system do when a user's preferences change slowly over 6 months? When their job changes? When they say something today that contradicts something from 2 years ago that they no longer believe but never explicitly retracted? This is the hard problem and nobody's measuring it.

If you've worked on feature stores or streaming pipelines, all of this should sound familiar. It's the same gap between "correctness on a static test set" and "actually behaves right in production over time". Memory benchmarks are still in the "static test set" era.

#### What I'm Actually Doing for Friday

For my own setup I'm running a hybrid:

- **LongMemEval-style synthetic** for the core retrieval correctness loop. I generated my own version on top of my real conversation patterns rather than the published benchmark, because Friday's domain (me, my work, my projects) doesn't match what's in LongMemEval.
- **A streaming-style eval** where I replay a week of conversations and check that questions answered on day 7 still work after day 14's ingestion has happened. This catches the "good at first, decays over time" failure mode.
- **A cost ledger** — tokens per write, tokens per read, storage growth — tracked alongside accuracy. Because if it's not deployable, it doesn't matter how accurate it is.

None of this is rigorous enough to publish. It's enough to stop me from shipping something broken. Which is the point.

---

#### Wrapping Up

If you only have time to look at one benchmark from this survey, look at LongMemEval. It's the closest thing to a standard and it covers more of the failure modes than the others. If you want the lifelong learning angle, StreamBench. Everything else is either narrow or proxy.

The bigger takeaway from the survey though is that the benchmark situation in agent memory is roughly where database benchmarking was in 1995 — everyone is running their own thing, comparisons are apples-to-oranges, and the questions that matter most for production (cost, drift, consistency over time) aren't being measured. There's room here for someone to do for memory what TPC did for OLTP. Probably won't be me but I'm watching for it.
